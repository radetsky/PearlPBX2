# PearlPBX2 — Швидкий старт

Два способи запустити PearlPBX2, залежно від того, що вам потрібно. Повний опис можливостей, архітектури та конфігурації — в [README.md](../../README.md).

## Вимоги

- **Варіант 1 (Ansible)**: голий хост Debian або Ubuntu, і все. `install.sh`
  сам встановлює Ansible, а `install.yml` розгортає решту —
  Python, PostgreSQL, Redis та Asterisk 22 (компілюється з вихідників) — на
  цільовому хості. Нічого встановлювати вручну заздалегідь не потрібно.
- **Варіант 2 (Docker Compose)**: лише Docker і Docker Compose. Весь стек
  (Python 3.10+/Django 5.2, PostgreSQL 14+, Redis 7+, Asterisk 22+ з
  `res_pjsip`/`res_agi`/`cdr_pgsql`) працює повністю в контейнерах.

## Що ви отримуєте одразу, "з коробки"

Свіжа інсталяція засіює робочу демо-АТС, а не порожню базу даних. Після
першого прогону міграцій/деплою у вас уже є:

| Внутрішні номери | Що це |
|---|---|
| `201`–`210` | 10 SIP-користувачів (`ppbxuser201`…`ppbxuser210`), випадкові паролі |
| `130` | Ехо-тест |
| `131` / `132` | Логін/логаут агента черги (`PauseQueueMember`) |
| `140` | Перевірити IVR із внутрішнього телефона |
| `141` | Черга Sales |
| `142` | Черга Support |

Плюс:

- Дві черги, **Sales** і **Support**, з усіма 10 користувачами як членами
- Англомовне IVR (`ivr-main`): "press 1 for Sales, press 2 for Support", 2 повтори при
  таймауті/невірній цифрі, потім fallback у Sales
- Приклад SIP-транка, `myprovider` (`csbc.myprovider.net`, користувач `test` / `secret`) —
  заглушка, яку треба замінити на реального провайдера (див.
  [Заміна прикладного транка](#заміна-прикладного-транка))
- Дві таблиці маршрутизації: **Incoming** (будь-який вхідний дзвінок → IVR) і **Outgoing**
  (усі 10 користувачів маршрутизуються через неї: внутрішні номери, `130`–`142`, та
  все інше — назовні через `myprovider`)

Все це засіює `manage.py seed_quickstart`, яка виконується лише один раз, на
свіжій інсталяції — див. [Нотатки / наступні кроки](#нотатки--наступні-кроки), як це гарантується.

## Варіант 1: Ansible (продакшн-інсталяція)

Потрібен хост Debian або Ubuntu (плейбук напряму використовує `apt` і systemd — інші дистрибутиви не підтримуються).

Розгортає Asterisk (компільований з вихідників), PostgreSQL, Redis, nginx, systemd-юніти та фаєрвол на свіжому хості — без ручних кроків:

```bash
git clone https://github.com/radetsky/PearlPBX2.git
cd PearlPBX2
sudo ./install.sh
```

`install.sh` сам встановлює Ansible, якщо потрібно, і запускає `ansible/install.yml` (додайте `-v` для докладного виводу Ansible), логуючи в `/var/log/pearlpbx2-install.log`. Після завершення створіть адміністратора:

```bash
./manage.sh createsuperuser
```

потім відкрийте `https://<ваш-хост>/admin/`.

Щоб пізніше підтягнути оновлення, запустіть `sudo ./update.sh` з тієї ж директорії — він запускає `ansible/update.yml`, який зберігає історію для відкату (`rollback.sh`) на випадок, якщо оновлення треба скасувати. `update.sh` ніколи повторно не засіює quickstart-дані, описані вище, тож його безпечно запускати на живій системі.

Дивіться `ansible/group_vars/all.yml` для змінних, які він використовує (директорія інсталяції, назва БД, версія Asterisk тощо), і `ansible/roles/` — що робить кожна роль.

## Варіант 2: Docker Compose (рекомендовано — для оцінки, розробки)

```bash
git clone https://github.com/radetsky/PearlPBX2.git
cd PearlPBX2

cp env.sample .env
# Відредагуйте .env — вкажіть креденшли БД, потім згенеруйте та впишіть:
#   DJANGO_SECRET_KEY:       openssl rand -hex 50
#   ASTERISK_MANAGER_SECRET: openssl rand -base64 48

docker compose up -d
docker compose exec django python manage.py createsuperuser
```

Відкрийте `http://localhost:8000/admin/`, увійдіть і одразу переходьте до
[Apply Changes](#apply-changes) — quickstart-дані вище вже є в
базі, їх лише треба один раз "виштовхнути" в Asterisk.

Нотатки:
- `django` автоматично прогоняє міграції та quickstart-посів при кожному старті (`docker-entrypoint.sh`) — ручний `migrate` не потрібен. Посів спрацьовує лише один раз; наступні рестарти — no-op.
- `asterisk-init` засіює мінімальний AMI-увімкнений `manager.conf` перед першим стартом Asterisk, тож `fastagi`/`dashboard-listener` одразу підключаються; "Apply Changes" пізніше перезаписує його реальним згенерованим конфігом з тими самими креденшлами.
- Callback-демон — опційний (він робить реальні вихідні дзвінки): `docker compose --profile callback up -d callback-service`.
- `docker-compose.override.yml` підхоплюється автоматично і дає контейнеру `django` hot-reload вихідного коду для локальної розробки; запустіть `docker compose -f docker-compose.yml up -d`, щоб його пропустити.

## Отримайте SIP-креденшли

Паролі 201–210 генеруються випадково і зберігаються тільки в базі даних.
В адмінці перейдіть у **SIP Users**, відкрийте **201** (або будь-якого іншого) і подивіться поле
**Password** — ця інструкція далі використовує **201** і **202**.

## Зареєструйте два софтфони

У будь-якому SIP-клієнті (Zoiper, Linphone, настільний телефон, …) зареєструйте два акаунти, використовуючи
креденшли вище:

- **Server**: хост/IP вашого PBX
- **Transport**: UDP, порт `5060`
- **Username / Password**: `ppbxuser201` / пароль з адмінки (і так само для 202)

## Apply Changes

Ніщо з вищесказаного не дійде до Asterisk, доки ви не натиснете застосування. В адмінці перейдіть у
**Admin → Apply Changes** (`/admin/apply`). Це перегенерує `extensions.ael`,
`pjsip.conf`, `queues.conf`, `queuerules.conf`, `manager.conf`, `musiconhold.conf`
та `confbridge.conf` з бази даних, робить бекап попередніх версій і
перезавантажує Asterisk. Зробіть це один раз зараз, і потім після кожної зміни через
адмінку.

## Тестові сценарії дзвінків

Робіть це по порядку — кожен наступний спирається на попередній.

| № | Сценарій | Набрати | Очікуваний результат / перевірка |
|---|---|---|---|
| 1 | Ехо-тест | `130` | Ви почуєте власний голос у відлунні. `asterisk -rx "core show channels"` покаже дзвінок. |
| 2 | Внутрішній дзвінок | 201 набирає `202` | 202 дзвонить. `asterisk -rx "pjsip show endpoints"` покаже обох як `Avail`. |
| 3 | Трансфер | Під час розмови, blind-трансфер через `#` або attended через `*`, ціль `202` або `141` | Див. [Трансфер](#трансфер) нижче |
| 4 | Вихід у зовнішній світ | Наберіть будь-який зовнішній номер | Не спрацює, доки не [замінити прикладний транк](#заміна-прикладного-транка). Потім `asterisk -rx "pjsip show registrations"` має показати `myprovider` як `Registered`. |
| 5 | IVR із внутрішнього телефона | `140`, потім натисніть `1` або `2` | Ви потрапите в Sales або Support. `asterisk -rx "queue show Sales"` покаже дзвінок. |
| 6 | Продакшн вхідний дзвінок | Подзвоніть на свій DID ззовні | Маршрутизується через **Incoming** → `ivr-main`. `asterisk -rx "pjsip set logger on"` — щоб побачити SIP-трасу наживо. |

(Docker Compose: перед кожним `asterisk -rx "..."` додайте `docker compose exec asterisk`.)

### Трансфер

Коди функцій трансферу беруться з `contrib/configs/features.conf`:
`#` = blind-трансфер, `*` = attended-трансфер (секція `[featuremap]`). Обидва
потребують опцій `t`/`T` у `Dial()`, через який прийшов дзвінок — вони вже присутні
в кожному засіяному екстеншені (наприклад, `Dial(PJSIP/${EXTEN}@myprovider,120,tT)`).

Ви можете зателефонувати з 201 абонента на 202 і підчас розмови натиснувши `#130#` ви переведете вашу розмову на ехо тест. Для вас дзвінок має закінчитись, а ваш абонент має почути вітання `demo-echotest`.

Після ініціації трансферу Asterisk резолвить набрані цифри через глобальну
змінну **`TRANSFER_CONTEXT`**, а не через контекст самого каналу —
засіяна як:

```
globals {
    TRANSFER_CONTEXT=Outgoing;
}
```

Саме тому користувачі на таблиці маршрутизації `Outgoing`: це дозволяє
цілі трансферу бути або внутрішнім номером (`_2XX`), або зовнішнім номером (`_X.`) через
`myprovider` — з одного, консистентного контексту.

## Заміна прикладного транка

`myprovider` (`csbc.myprovider.net` / `test` / `secret`) — це заглушка, вона
ніколи не зареєструється. В **Admin → SIP Uplinks and Peers → myprovider** замініть:

- `registration_uri` / `contact_uri` / `match_hosts` — хостнейм SBC вашого провайдера
- `username` / `secret` — креденшли вашого акаунта

Потім [Apply Changes](#apply-changes) і перевірте:

```bash
asterisk -rx "pjsip show registrations"
```

`myprovider` має перейти зі стану `Rejected`/`No response` у `Registered`.

## Нотатки / наступні кроки

- **Міжнародні дзвінки заблоковані за замовчуванням.** Таблиця `Outgoing` маршрутизує
  `_00X!` (міжнародні префікси) у контекст `international-calls`, який
  просто розриває виклик — безпечний дефолт, щоб свіжа інсталяція з прикладними креденшлами
  ніколи не стала вектором toll fraud. Видаліть або перенаправте цей
  `DialplanExtension`, коли будете готові дозволити такі дзвінки.
- **`Outgoing` проти легасі-таблиці `PEARLPBX`.** `PEARLPBX` досі існує (це
  `settings.PEARLPBX_DEFAULT_ROUTING_TABLE`, використовується як fallback в інших місцях), але жоден
  SIP-користувач більше не маршрутизується через неї після запуску quickstart-посіву — всі
  вони на `Outgoing`.
- **Кілька транків / маршрутизація за найменшою вартістю.** Засіяний контекст `outbound-external`
  набирає `myprovider` напряму. Для кількох транків перейдіть на
  `AGI(agi://127.0.0.1:4573/dial-trunk-group,...)` — див.
  `services/fastagi/README.md` для груп транків із фейловером.
- **Музика на утриманні (MOH)** для черг використовує `contrib/moh/on_hold_music.wav` — замініть
  файли в класі MOH `default` на власні.
- **Запис розмов** не увімкнений за замовчуванням; налаштування `MixMonitor` див. в
  [admin-guide.md](admin-guide.md).
- **Сам quickstart-посів** — це `manage.py seed_quickstart`; вона перевіряє,
  чи вже існує будь-яка `Queue`, `SIPPeer` або таблиця маршрутизації `Incoming`/`Outgoing`,
  і нічого не робить, якщо так — тож її безпечно запускати вручну. Ansible-івський
  `install.yml` викликає її один раз, з тим самим гейтом "перша інсталяція на цьому хості",
  що й для генерації секретів; `update.yml` її взагалі не викликає.
