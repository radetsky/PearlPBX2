# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Added

- **Automatic TLS certificate provisioning for nginx (WebRTC wss)** — the nginx Ansible role now provisions a working HTTPS/`wss://` certificate on a fresh install with no manual step, in three tiers: (1) a domain is given (`--domain`) → Let's Encrypt via HTTP-01 webroot, 90-day cert, standard renewal; (2) no domain but a public IPv4 is detected → Let's Encrypt's short-lived **IP-address certificate** (`--preferred-profile shortlived`), 6-day validity renewed every 4h by a systemd timer, falling back to an external IP lookup for NAT'd cloud hosts with no locally-visible public address; (3) neither is reachable → a self-signed fallback, now with a proper `subjectAltName` (previously CN-only, which modern browsers/clients reject) and capped at 397 days (Apple's 398-day hard limit, was 3650). `certbot` is installed into a dedicated pip venv at `/opt/certbot` since Debian/Ubuntu ship certbot 2.x and IP-address certs require ≥ 5.4. The vhost's `ssl_certificate`/`ssl_certificate_key` always point at stable symlinks, redirected to whichever source is active, so nginx config never needs to know which tier provisioned the cert. `install.sh`/`quickstart-install.sh` gained `--domain`/`--email` flags (and `PEARLPBX2_DOMAIN`/`PEARLPBX2_EMAIL` env vars), `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` include the domain when set, and the closing install message reflects which tier ran (read from `/etc/PearlPBX/tls-mode`).
- **Quickstart now seeds 10 WebRTC (wss) demo users** — `seed_quickstart` creates a `transport-wss` `SIPTransport` and `webrtcuser1`..`webrtcuser10` `SIPUser`s (each a random 16-char password) on the `Outgoing` routing table, so a fresh install has working browser-calling test accounts out of the box. Under Docker (`PEARLPBX2_DOCKER=1`), the seeded users get `disallow=all` / `allow=g722,ulaw,vp9,vp8,h264` custom settings instead of the default Opus-first allow list — the `andrius/asterisk:22` image ships the Opus SDP/runtime library but not the `codec_opus.so` translator, so negotiating Opus there fails every `Playback()` with "Unable to find a codec translation path"; bare-metal/Ansible installs are expected to have Opus compiled in and are unaffected.
- **`Settings.local_users_dial_template`** — the per-user AEL body used by `core.conf.make_local_users_context()` for every active SIP user's entry in the auto-generated `PEARLPBX-Users` context is now an editable template (migration `0082_settings_local_users_dial_template.py`), with `${SIPUser.username}` substituted per user before rendering (other `${...}` placeholders are native Asterisk variables and pass through unchanged). This replaces the previous approach of writing one `DialplanExtension` row per `SIPUser` as a `save()`/`delete()` side effect — a design that silently missed any `SIPUser` created through a Django migration or bulk `bulk_create()`, since Django's historical models used during migrations bypass custom `save()` logic entirely. Migration `0083_repoint_pearlpbx_local_users.py` cleans up the now-unused stored rows. See also the `PEARLPBX-Users` context protection entry below, which builds on the same `make_local_users_context()`.
- **SIP User admin form shows the realm and MD5 credential (HA1)** — `SIPUserAdmin` gained read-only `realm_display`/`md5_cred_display` fields next to `secret`, so an admin can copy the RFC 2617 HA1 hash (`MD5(username:realm:password)`) that WebRTC/hardware-phone provisioning sometimes needs, without opening a shell.
- **`fastagi` `dial-trunk-group` AGI: configurable dial timeout and `Dial()` options** — the AGI previously hardcoded `Dial(..., "120", "rtT")` on every retry attempt; it now accepts two additional positional AGI arguments (dial timeout in seconds, `Dial()` options string), defaulting to new `DIAL_TRUNK_GROUP_TIMEOUT`/`DIAL_TRUNK_GROUP_OPTIONS` env vars (120 / `tT`) when the dialplan call omits them. Documented in `services/fastagi/README.md`.
- **`make` convenience targets for Docker** — `make docker-up` (background, no dev override), `make docker-dev` (foreground, hot reload), `make docker-stop`, `make docker-clean`, plus a `make help` default target listing all targets.
- **Docker Asterisk container hardening** — a real `healthcheck` (`asterisk -rx "core show channels count"`) now gates the `django` service's `depends_on`, so Django no longer starts against an Asterisk that hasn't finished booting; `docker/asterisk-bootstrap.sh` also now loads `res_srtp.so` (missing from the vendor image's default `modules.conf`, and required for WebRTC's DTLS-SRTP — without it every wss call failed to negotiate media) and downloads the official `asterisk-core-sounds-en-gsm` package into a new `asterisk_sounds` named volume, since the vendor image ships `/var/lib/asterisk/sounds` completely empty (no stock prompts at all, so `demo-echotest`, `agent-loginok`, the `queue-*` prompts, etc. were silent). The named volume also fixes a pre-existing bug where the image's own `VOLUME /var/lib/asterisk/sounds` declaration shadowed that subpath of the broader `asterisk_lib` mount with an anonymous volume, making custom sound files invisible to Asterisk. `contrib/configs/http.conf`'s `bindaddr` changed from `127.0.0.1` to `0.0.0.0` (PJSIP's `wss` transport rides Asterisk's built-in HTTP server, which must be reachable from outside the container), and `docker-entrypoint.sh` now runs `seed_quickstart`/`apply_changes` only once, gated on a marker file on the shared `asterisk_config` volume, mirroring `ansible/install.yml` (a redeploy previously re-ran the full quickstart seed on every container start).
- **REST API: CRUD for `DialplanContext`, `DialplanExtension`, `DialplanMacro`** — closes the largest remaining API gap: the dialplan text that every rename/delete guard (`TrunkGroup`, `Queue`) already scans could previously only be edited through the admin.
  - `apps/api/views/dialplan.py` exposes `/api/v1/dialplan-contexts/`, `/api/v1/dialplan-extensions/`, `/api/v1/dialplan-macros/` (staff-only). All three models now inherit `AuditFields` (migration `0089_dialplan_audit_fields.py`), which also adds `validators=[validate_ael_variable_name]` to `DialplanMacro.name` (it previously accepted any string, including hyphens/spaces that break the generated `macro name() {` AEL block).
  - **`DialplanMacro` gained the same three-layer dialplan-reference guard** as `TrunkGroup`/`Queue`: `DialplanMacro.find_dialplan_references()` scans `DialplanExtension.dialplan`, other macro bodies, and `Settings.local_users_dial_template` for a literal `&name();` AEL macro call (case-sensitive, since AEL resolves macro calls by exact name — unlike `Queue`'s case-insensitive `strcasecmp()` lookup). Renaming or deleting a macro still called that way is rejected at the model level (`clean()`/`delete()`), the admin (`DialplanMacroAdmin` via the existing `DialplanGuardedDeleteAdminMixin`), and the API (`400`/`409` via the existing `DialplanGuardedDestroyMixin`). This is a best-effort text scan — it can't see a call reached only through an Asterisk variable, and it can't see the Python-level `DEFAULT_LOCAL_USERS_DIAL_TEMPLATE` fallback used when no `Settings` row exists or the field is blank.
  - **The auto-generated `"PEARLPBX-Users"` context is now protected.** It's rendered live from `SIPUser` data by `core.conf.make_local_users_context()` and excluded from `make_dialplan_contexts()` — a `DialplanExtension` stored inside it would silently never reach `extensions.ael`, and renaming the row would make it render twice under two names (the live version plus a stale one from its old stored extensions). `DialplanContext.clean()`/`delete()` now reject renaming or deleting this reserved context, and `DialplanExtension.clean()` now rejects creating an extension inside it (previously only checked by `DialplanExtensionSerializer.validate_context()` at the API layer, leaving the admin's `DialplanExtensionForm` able to save one silently). `DialplanContextAdmin.has_delete_permission()` hides the delete button.
  - **`DialplanContext.delete()` now also guards `Webhook.contexts`**, a plain M2M with no `PROTECT` — mirroring the existing `RoutingTable.delete()` guard for `Webhook.routing_tables`. Deleting a context still referenced by `DialplanExtension.context`/`RoutingRecord.context` (both `PROTECT`) already returned `409` for free via the existing `ProtectedError` branch in `apps.api.exceptions`.
  - `DialplanExtensionSerializer.context` is required even though nullable in the DB, for the same reason as `RoutingRecordSerializer.context` — `make_dialplan_contexts()` only emits extensions grouped under a context. Its `dialplan` field's validation (Asterisk AEL syntax, and that any `&macro();` call references an existing `DialplanMacro`) comes for free from the model's existing `validate_dialplan_field`; create a macro before an extension that calls it. `(context, ext)` uniqueness uses an explicit `UniqueTogetherValidator` rather than DRF's automatic `Meta.constraints` detection, since the latter injects `default=None` for the nullable `context` field, which conflicts with the serializer's own `required=True` override.
  - Documented in `docs/{en,ua,es}/API.md`.
- **REST API: CRUD for `PhoneDevice`, `Queue`, `QueueMember`** — three new staff-only resources:
  - `apps/api/views/phone_devices.py`'s `PhoneDeviceViewSet` exposes `/api/v1/phone-devices/`. `mac_address` validation (accepts separators/mixed case, normalizes to `XX:XX:XX:XX:XX:XX`) moved from `PhoneDeviceForm.clean_mac_address()` to a reusable `core.validators.validate_mac_address()`. A new `POST /api/v1/phone-devices/<id>/provision/` action wraps `PhoneProvisioningManager.provision_device()` — the same thing the admin's "Apply configurations" button does, for one device over the API.
  - `apps/api/views/queues.py` gained `QueueViewSet`/`QueueMemberViewSet` (DB config) alongside the existing AMI-backed `QueueMemberPauseView`/`QueueMemberListView` (live runtime state) — the module docstring and each resource's docs now spell out the difference, since `GET /api/v1/queue-members/` and `GET /api/v1/queues/members/` both answer "who's in this queue" from entirely different sources of truth. `Queue`/`QueueMember` now inherit `AuditFields` (migration `0088_queue_queuemember_audit_fields.py`); `QueueAdmin`/`QueueMemberAdmin` use `AuditAdminMixin`.
  - `Queue.name` is looked up by Asterisk's `app_queue` from a literal `Queue(<name>,...)` AEL app-call embedded in dialplan text — renaming or deleting a queue while `Queue.find_dialplan_references()` finds such a reference is rejected at the model level (`clean()`/`delete()`), the admin (`QueueAdmin.has_delete_permission()`), and the API (`400`/`409`), mirroring `TrunkGroup`'s existing guard. Unlike that guard, the match is case-insensitive (`re.IGNORECASE`) — `app_queue` resolves queue names with `strcasecmp()`, so a differently-cased dialplan call really does reach the queue.
  - `QueueSerializer.strategy` is required even though nullable in the DB — `core.conf._make_single_queue_config()` interpolates it with no null guard (`f"strategy={queue.strategy}"`), so an empty value would literally emit `strategy=None` into `queues.conf`. `QueueMemberSerializer.interface` reuses `validate_asterisk_interface` (previously only applied to the AMI pause endpoint, never to the model itself); `member_name` defaults to `""` instead of allowing `null`, since a null value renders as the literal word `None` in the generated `member => ...` line. A given `(queue, interface)` pair must be unique (`UniqueTogetherValidator`, `400` on conflict).
  - Documented in `docs/{en,ua,es}/API.md`.
- **REST API: CRUD for `RoutingRecord`** — `apps/api/views/routing_records.py`'s `RoutingRecordViewSet` exposes prefix-based routing rules under `/api/v1/routing-records/` (staff-only, like the other resources in this API). `RoutingRecord` now inherits `AuditFields` (migration `0087_routingrecord_audit_fields.py`). `context`/`routing_table` are required at the API layer even though nullable in the DB — `core.conf.make_routing_tables()` interpolates `context` with no null guard (a null value would literally emit `goto None,${EXTEN},1;` into the generated dialplan), and a record with no `routing_table` never appears in any table's generated block. `?name=`, `?prefix=`, `?routing_table=`, `?context=`, `?search=` filters. Documented in `docs/{en,ua,es}/API.md`.
- **REST API: `secret`/`md5_cred`/`priv_key_file` are hidden in list responses** — `SIPUserSerializer`/`SIPPeerSerializer` (`secret`, `md5_cred`) and `SIPTransportSerializer` (`priv_key_file`) now return `null` for these fields on `GET /api/v1/sip-users/`, `/sip-peers/`, `/sip-transports/` (the paginated list), via a new `HideSensitiveInListMixin` keyed off `view.action == "list"`. The real value is still returned by `GET .../<id>/` and by the object `POST`/`PATCH` return — this only keeps credentials out of a bulk dump. `cert_file`/`ca_list_file` (public certificate material) are unaffected.
- **REST API: `RoutingTable`/`TrunkGroup` CRUD, an `Apply Changes` wrapper, and automatic queue-member cleanup** — three follow-ups from reviewing what happens when a `SIPUser` is deleted:
  - `apps/api/views/routing_tables.py`/`trunk_groups.py` expose `/api/v1/routing-tables/` and `/api/v1/trunk-groups/` (staff-only, like the other SIP resources). Both models now inherit `AuditFields` (migration `0086_routingtable_trunkgroup_audit_fields.py`). `RoutingTableSerializer.validate_name()` pre-checks the `DialplanContext` name collision that `RoutingTable.save()` previously raised as a plain Django `ValidationError` — a class `api_exception_handler` didn't catch, so it surfaced as a raw `500`; a new generic `DjangoValidationError → 400` branch in `apps.api.exceptions` now backstops that class of bug everywhere, not just here. Deleting a routing table still used by a `Webhook`'s routing-table filter (an M2M with no `PROTECT`) now returns `409` instead of silently unlinking it.
  - `TrunkGroup.name` is looked up by `services/fastagi/fastagi.py` via raw SQL from a literal `dial-trunk-group,<name>,` AGI call embedded in dialplan text — renaming or deleting a group while `TrunkGroup.find_dialplan_references()` finds such a reference is now rejected at the model level (`clean()`/`delete()`, so it's enforced for admin and shell too), the admin (`TrunkGroupAdmin.has_delete_permission()` hides the delete button instead of a 500), and the API (`400`/`409`). This is a best-effort text scan — it can't see a name reached only through an Asterisk variable.
  - `apps/api/views/config.py` wraps the admin's "Apply Changes" page: `GET /api/v1/config/preview/` is the existing dry-run (generated file contents, no writes, no reload) the admin already showed on GET, now available over the API; `POST /api/v1/config/apply/` writes configs and reloads Asterisk with a required `mode: "soft"|"hard"` field (unlike the admin form, where anything but the literal string `"soft"` silently means a hard restart). Both require a new `IsSuperUser` permission — the existing `IsStaff` would have been a privilege escalation for an action that can restart Asterisk and drop every call. A short-lived Redis lock (fails open if Redis itself is down) returns `409` for a concurrent apply. `pbx.admin.ApplyChangesView.apply_changes()`/`create_configuration_file()` now return which files actually changed, surfaced as `changed_files` in the response.
  - `core/signals.py` (wired from `CoreConfig.ready()`) deletes a `SIPUser`'s `QueueMember` row(s) on `post_delete` — `QueueMember.interface` is free text (`"PJSIP/{username}"`), not a foreign key, so nothing else cleaned it up and a deleted extension stayed in `queues.conf` as a permanently-unavailable member. New `python manage.py cleanup_orphan_queue_members --dry-run` sweeps rows orphaned before this signal existed. Documented in `docs/{en,ua,es}/admin-guide.md` and `API.md`.
- **REST API: full CRUD for SIP transports and peers** — `apps/api/views/sip_transports.py`'s `SIPTransportViewSet` and `apps/api/views/sip_peers.py`'s `SIPPeerViewSet` expose `SIPTransport`/`SIPPeer` under `/api/v1/sip-transports/`/`/api/v1/sip-peers/`, closing the gap left by the SIP-users CRUD below: a `SIPUser` requires a `transport`, but there was no way to provision one without the admin. Same `IsStaff`-on-every-method rule (transports return TLS private keys, peers return plaintext `secret`/`md5_cred`). Both models now inherit `AuditFields` (migration `0085_siptransport_sippeer_audit_fields.py`) and use `AuditAdminMixin` in the admin. `SIPTransportSerializer` normalizes a blank `local_nets` to `null` (a bare `local_net = ` line otherwise lands in `pjsip.conf`) and validates each entry as a CIDR network; `SIPPeerSerializer` renames the model's camelCase `registrationHere`/`registrationThere` to `registration_here`/`registration_there` and requires `registration_uri`/`username` whenever `registration_there` is set, since `core.conf.__section_trunk_remote_registration()` otherwise skips the section silently. Deleting a transport still referenced by a `SIPUser`/`SIPPeer`, or a peer still in a `TrunkGroup`, now returns `409 Conflict` (new `apps.api.exceptions.Conflict`, plus a `ProtectedError` branch in `api_exception_handler`) instead of a raw 500 or a silent partial delete. Documented in `docs/{en,ua,es}/API.md`.
- **REST API: full CRUD for SIP users** — `apps/api/views/sip_users.py`'s `SIPUserViewSet` exposes `SIPUser` (SIP extensions) under `/api/v1/sip-users/` (list/create/retrieve/update/partial_update/delete), with `?username=`, `?extension=`, `?search=` filters. Unlike the rest of the API, every method — including `GET` — requires a staff or superuser token (new `apps/api/permissions.IsStaff`), since the resource returns dial-out credentials (`secret`) plus the derived `realm`/`md5_cred` (RFC 2617 HA1) that WebRTC endpoints authenticate with regardless of the stored `auth_type`. `SIPUser` now inherits `AuditFields` (migration `0084_sipuser_audit_fields.py`), recording `created_by`/`modified_by` on both API and admin writes, matching `Blacklist`/`Whitelist`/`Contact`/`PhoneDevice`. The validators shared with `SIPUserForm` (`validate_alphanumeric`, `min3len`; plus `validate_sip_username`, used by `SIPPeerForm`) moved from `core/forms.py` to `core/validators.py` so the serializer can reuse them without importing Django forms. Writing through this endpoint only updates the database — Asterisk still needs "Apply Changes" in the admin to pick up the change. Documented in `docs/{en,ua,es}/API.md`.
- **Daily "longest calls" email report** — `python manage.py mail_report` sends a top-N table of the previous day's longest calls, with a link to each call's recording, to `MAIL_REPORT_RECIPIENTS`. Query logic lives in `apps/reports/services/longest_calls.py` (de-duplicates CDR legs sharing a `uniqueid`, keeping the longest); new `EMAIL_*`/`MAIL_REPORT_*` settings in `pbx/settings.py`; new Ansible cron task `pearlpbx2_mail_report` (daily at 06:00, installed only when `pearlpbx2_mail_report_recipients` is set).

### Fixed

- **WebRTC (wss) SIP users were dialed into a context that was never generated** — `__make_pjsip_conf_webrtc_user()` in `core/conf.py` emitted `context=<username>` for every WebRTC endpoint instead of the user's routing table, but nothing in `make_dialplan_contexts()`/`make_routing_tables()` ever generates a context named after a username — so an inbound call from a WebRTC user landed in a nonexistent context and went nowhere. Now uses `user.routing_table.name`, matching how regular (non-WebRTC) endpoints are generated.
- **AEL dialplan validator didn't check `goto`/`Goto()` targets** — a bare `goto +0681231231,1;` (leading unquoted `+`) passed Django's validation but was rejected by Asterisk's AEL compiler at reload time with a syntax error. `core/validators.py` now validates both the bare-`goto` and `Goto()` call forms.
- **Stray spaces in generated AEL `globals { }` block** — `make_dialplan_globals()` in `core/conf.py` emitted `name = value;` (spaces around `=`); changed to `name=value;` to match Asterisk AEL's expected global-assignment syntax.
- **Debian installs missing `cron`** — `cron` wasn't in the `system` Ansible role's package list, so the daily backup/report cron jobs installed by other roles silently had nothing to run them on a fresh Debian host (only Ubuntu, where `cron` is typically preinstalled, worked by accident).
- **Firewall installer's SSH-port confirmation could hang an unattended install** — the Ansible `firewall` role's SSH-port detection previously stopped with an interactive `pause: prompt: "Press Enter to continue"`, blocking any install run without a TTY (e.g. `ansible-pull`, CI). It now only logs the detected port via `debug` and proceeds.
- **`AudioFileByUniqueidView` returned HTTP 500 for every request** — it was missing from `ReportViewPermissionMixin.VIEW_PERMISSION_MAPPING` (`apps/reports/mixins.py`), so `get_permission_required()` always raised `ImproperlyConfigured` regardless of the caller's permissions. Found while wiring recording links into the new `mail_report` command.
- **nginx HTTP→HTTPS redirect broke Let's Encrypt HTTP-01 validation** — the generated vhost's `return 301 https://...` sat directly in the `server` block, which nginx evaluates during the server-rewrite phase, before location matching — so it fired for the `^~ /.well-known/acme-challenge/` location too, and the ACME client's HTTP-01 request never reached the challenge file. `ansible/roles/nginx/templates/pearlpbx2.nginx.j2` now wraps the redirect in a `location /` block, so the more specific acme-challenge location takes precedence.

### Changed

- **`asterisk_version` pinned to `22.11.0`** (`ansible/group_vars/all.yml`) instead of the floating `22-current`, so a fresh install always builds a known-good version rather than whatever is newest on install day.
- **`install.sh`'s post-install output trimmed** — the optional-integration instructions (MP3 backup sync, Slack server alerts, Slack unmatched-call notifications) and interrupted-install recovery notes moved out of the script's echoed output and into `docs/{en,es,ua}/quickstart.md`, which the script now points to instead of printing everything inline.

## [2.7.2] - 2026-08-23

### Added

- **SIP trunk `[identify]` escape hatch: `custom_identify_settings`** — `SIPPeer` gained a free-text field for the body of the generated `[identify]` section (migration `0081_sippeer_custom_identify_settings.py`), exposed in the admin's "Advanced" fieldset next to `custom_aor_settings`. `core/conf.py`'s `[identify]` generation previously only supported IP-based `match`, which can't distinguish multiple lines behind the same source IP — e.g. a GSM gateway where each of 4 ports registers from the same address and inbound calls only carry a distinguishing `Contact: 0001` header. When the field is set, `__section_trunk_endpoint()` also derives `identify_by` from its content instead of the old single `identify_by=ip` check: `header` if the text contains `match_header`, `ip` if it contains `match=`, plus `username` whenever `registrationHere` is enabled. This isn't cosmetic — Asterisk's `identify_by` default (`username,ip`) has no `header` value, and REGISTER-to-AOR resolution requires listing a method Asterisk documents as AOR-capable (only `username` qualifies among the ones used here), so a header-matched trunk that also registers needs both `header` (for inbound INVITEs, since From/To carry real phone numbers, not the port id) and `username` (for REGISTER, since the gateway's own username per line does match the AOR name) at once. Trunks that leave the field empty are unaffected — `identify_by=ip` is still emitted exactly as before. Covered by new tests in `core/tests.py`.
- **REST API: pause/unpause and list queue members** — `POST /api/v1/queues/members/pause/` sends AMI `QueuePause` for a given `interface` (optionally scoped to one `queue`), and `GET /api/v1/queues/members/` (optional `?queue=<name>`) returns live member status (paused, status, calls taken, ...) via AMI `QueueStatus`. Both talk to Asterisk directly, independent of the dashboard's Redis-backed state, so they work even without `dashboard-listener` running. `core/ami.AsteriskManagementInterface` gained `queue_pause()` and `queue_members()`; the dashboard's existing `pause_queue_member()` view now goes through the same wrapper instead of opening its own AMI connection. New validator `core.validators.validate_asterisk_interface` guards the `interface` field against AMI injection. AMI timeouts (all in seconds) are now named settings instead of scattered magic numbers: `ASTERISK_AMI_DEFAULT_TIMEOUT` (long-running admin actions like reload/restart), `ASTERISK_AMI_QUICK_TIMEOUT` (pause/status/hangup-style actions), `ASTERISK_AMI_RESPONSE_MARGIN` (slack added on top of an Originate's own `timeout_ms`).
- **Docker integration test suite against a real Asterisk** — `tests/integration/test_queue_members.py` seeds a real Queue + PJSIP `QueueMember`, applies the generated config the same way "Apply Changes" does, reloads a live `andrius/asterisk:22` container, and drives `POST /api/v1/queues/members/pause/` / `GET /api/v1/queues/members/` against it — confirming pause state actually changes in Asterisk, not just that the right AMI calls were made. New isolated stack `docker-compose.integration.yml` (own volumes/DB/network, no host ports), run via `make integration-test`. Opt-in in CI (`.github/workflows/integration-test.yml`, push to main/master or manual dispatch) rather than on every PR, since it takes tens of seconds versus the existing mocked suite's seconds.
- **CRM webhooks: separate outgoing-call event chain** — new events `call.outgoing` / `call.outgoing_answered` / `call.outgoing_ended`, fired for calls placed by a SIP user (never a trunk), independent of the existing inbound chain (`call.incoming` / `call.answered` / `call.missed` / `call.ended`). `Webhook` gained `send_outgoing`, `send_outgoing_answered`, `send_outgoing_ended` (migration `0005_webhook_outgoing_events.py`); each requires at least one selected routing table, mirroring how inbound events require a context or queue. New payload fields `direction` (`"inbound"`/`"outbound"`), `dest_channel`, `dial_status`, `answered`. Outgoing-call detection is endpoint-based, not context-based: both a SIP user and a trunk can end up with a PJSIP context equal to a routing table's name, so `apps/webhooks/sync.py` now serializes a `sip_users` map (`{endpoint: routing_table}`, SIP users only) into `webhooks:config`, and `webhook_sender.extract_endpoint()` resolves the AMI channel's endpoint against it — a trunk's channel never matches, even sharing a routing table's name with a SIP user. `services/dashboard/dashboard_listener.py` wires `AMI DialEnd` (`DialStatus=ANSWER`) to `call.outgoing_answered`, closing a gap noted in the previous release (direct/non-queue calls previously had no "answered" signal at all).
- **CRM webhooks: `linkedid`, `channel`, `channel_vars`; system-channel filter** — every event now carries `linkedid` (Asterisk's own cross-channel call-correlation id, read from AMI `Linkedid`) and `channel` (the channel name), so a CRM can group separate webhook deliveries belonging to the same logical call without guessing from `uniqueid` proximity or timestamps. New `channel_vars` object exposes allow-listed Asterisk channel variables (env `WEBHOOK_CHANNEL_VARS`, default `ULINE` — e.g. `services/fastagi`'s parking-slot allocator), tracked via the existing `VarSet` handler and echoed on every event where the variable is already known. `call.outgoing` (and its `outgoing_answered`/`outgoing_ended` chain) is now skipped by default for a channel Asterisk created via `Dial()`/`Originate()` that has not yet been `Goto()`'d to a real extension (`exten` still the dialplan placeholder `"s"`) — pure system noise for a CRM; set env `WEBHOOK_SEND_SYSTEM_CHANNELS=true` to restore the old behavior. ### Changed
